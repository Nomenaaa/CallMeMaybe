# Description

`CallMeMaybe` is a project that aims to generate a precise function call with typed arguments from a Natural Language prompt request using LLMs (Large Language Models). 

The goal is to constrain the model output so it produces valid JSON and selects the correct function name and parameters from a predefined catalog. 

The challenge is to guides the model's output to produce 100% valid JSON format and ensure near-perfect accuracy (90%+) using small LLMs: `Qwen/Qwen3-0.6B`.

The program reads both prompt data and function definitions from JSON files located in the `data/input` directory by default. Generated results are written to the `data/output` directory unless custom path is provided.

## Installation
To install all program dependencies and create a virtual environment automatically:

```
make install
```
**Note**: the installation needs at least 10GB. The model cache and virtual environment can be redirected to a custom location if needed:

```
export HF_HOME=/path/to/export/.llm
export UV_CACHE_DIR=/path/to/export/.uv_cache
export UV_PROJECT_ENVIRONMENT=/path/to/export/.venv
```
## Execution
To run the program with default configuration:

```
make run
```
or run it directly with `uv`:
```
uv run python -m src
```

To use custom input and output files, pass the CLI arguments:

```
uv run python -m src [--functions_definition <function_definition_file>] [--input <input_file>] [-output <output_file>]
```

# Algorithm explanation

The project uses constrained decoding to keep generation valid.

The main idea is simple: before choosing the next token, the system filters the model's possible next tokens against a set of valid continuations defined by the current state.

The constraints are built from:
- a trie structure for valid strings such as function names and boolean values
- deterministic finite automata (DFA) for pattern-based values such as strings, integers, and numbers

For each state, the program extracts the valid next-token IDs, decodes them, and simulates the transition to the next state. These valid tokens are cached to avoid recomputing the same state repeatedly.

The generation loop continues until the current state is accepting. At each step:
1. the model produces logits for the next-token distribution,
2. invalid tokens are set to `-inf`,
3. the model selects the token with the highest remaining probability.

This ensures the output follows the allowed grammar while still being generated by the LLM.

# Design decisions

Several implementation choices were made to keep the system modular and reliable:

- `Constraint` abstraction: all constraints share a common interface through polymorphism, so the main decoder function can work with different automata without special cases.
- State-based execution: the generator only needs the current state and the next character or token to decide whether a transition is valid.
- Caching: previously computed valid-token sets are stored by state to reduce repeated computation and improve runtime.
- Validation layer: structured checks ensure that generated data matches expected schema rules before it is accepted.

# Performance analysis

The current implementation is designed for reliability rather than maximum speed.

- Accuracy: output quality is high, with near-perfect validity in constrained cases.
- Speed: the runtime is acceptable for small batches of prompts and function definitions, usually staying within a few minutes for limited datasets (about 102secs for 11 prompts and 05 functions definitions).
- Reliability: the use of constraints and validation significantly reduces malformed JSON and invalid argument types.

# Challenges faced

The main difficulties were:

- understanding how small LLMs generate token-by-token output and how to safely constrain that behavior.
- designing prompts that consistently lead the model toward the correct function choice and argument extraction.
- ensuring the final JSON is both valid and semantically correct for each function definition.

These challenges were faced through experimentation, prompt refinement, documentation and the help of peer-to-peer.

# Testing strategy

The implementation was validated in several ways:

- installing the required dependencies in the project environment.
- validating the provided dataset files against the expected schema.
- running the generate function on prompt batches and checking whether the outputs matched the required structure and correctness.
- using additional prompt/function combinations to test edge cases and malformed generations.

# Example usage

A typical run of the project looks like this:

```bash
make run
```

This reads the default files from `data/input`, generates the function-call outputs, and stores the results in `data/output`.

Example generated result:

```json
{
  "prompt": "What is the sum of 2 and 3?",
  "name": "fn_add_numbers",
  "parameters": {
    "a": 2.0,
    "b": 3.0
  }
}
```

This demonstrates the central behavior of the project: converting a prompt into a valid, typed function-call object using constrained decoding.
